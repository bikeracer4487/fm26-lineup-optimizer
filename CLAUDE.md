## What this project is

The FM26 lineup optimizer is being rebuilt as a native Mac app for Football Manager 27: SwiftUI, with the selection engine rewritten in Swift, for one save on this Mac. The Python and Electron code in this repository is the old version. It is kept as reference while the new one is built, and it is removed at the end.

## New code: `LineupEngine/`

A Swift package (Swift 6, macOS 26, Swift Testing, Foundation only). Built so far: the domain model, the FMRTE clipboard importer, the squad book, the FM27 role catalogue and tactics, the rating core, fitness and risk rules, an exact assignment solver, lineup selection with a reason for every pick and omission, the planner (looking ahead across fixtures, with each player's jadedness trend measured from readings kept at each import), and the advisors (First and Second XI, Depth, Rest, Training, Player Removal, Mentoring, a suggested importance for each fixture, a game plan for a simulated match, Scouting, the terms to propose when a player is sold or loaned out, and who is in the last year of his contract with a reasonable wage range). The app is a second package, `LineupApp/`, described below. The engine has no UI and reads no files itself; it is handed data.

Test it with:

    cd LineupEngine && swift test

Run one suite or test with `swift test --filter <name>`. Test output must be clean: no build warnings. The suite has 1,802 tests after wages by the year (27 November 2026, when the Mac was under other load and it took 132 and 219 seconds); 1,800 took about a minute (60 seconds) on 26 November 2026, after the picker's current rating (1,790 in 60 seconds earlier that day, after the Contracts screen, the wage range and the fixes that followed their whole-branch review; 1,727 in 55 seconds on 25 November 2026, before them).

Try it on the captured squad (prints the lineup with reasons; add `--profile both` to compare rating profiles):

    cd LineupEngine && swift run -q lineup-cli select \
      --grids Tests/LineupEngineTests/Fixtures/captures/first-team.grids.json \
      --tactic Tests/LineupEngineTests/Fixtures/tactics/sample-4231.json \
      --first-team Tests/LineupEngineTests/Fixtures/captures/first-team.tsv \
      --u21 Tests/LineupEngineTests/Fixtures/captures/u21.tsv --own-club "Oxford City"

Plan the next five fixtures for the same squad (prints each lineup with reasons, then who starts where; add `--saving 0` to turn off saving players for bigger fixtures, and `--development 0` to turn off the favour to young players; the default is 1):

`advise` also prints mentoring groups. They are guesses from the hierarchy and ages, and none until a hierarchy is entered; the command line takes no arrow readings. Add `--standings <file>` to enter one: a JSON object from a player's key to his hierarchy level and social group (the format is described at the top of `main.swift`). Add `--league-situation title-race|in-contention|mid-table|nothing-to-play-for` to say where the club stands in the league; it changes the suggested importance of league fixtures only, and it is the choice by hand, which wins over a table (without either, every league match is in contention). Add `--league-table <paste.tsv>` and `--league-format <promoted>,<play-offs>,<relegated>`, both or neither, to read the league table: the paste is read through `--grids`, which must then carry FMRTE's standings layout as well as the squads' (`Tests/LineupEngineTests/Fixtures/captures/first-team-and-league.grids.json` holds both, for the rebuilt table `league-table.tsv` beside it, with `--league-format 1,6,4`). `advise` then prints a League part before the importances (the bye line, the reading's sentences, a note when the order was worked out, the paste's warnings and the evidence note), and the table speaks for the next league fixtures in `--fixtures`, `--as-of` standing for the day it was pasted and `--history` saying which are confirmed. `scout` takes neither. `plan` and `advise` also take `--fitness-readings <file>`, a JSON object from a player's key to his readings (`FitnessReading`'s own form, described at the top of `main.swift`), to measure each player's jadedness trend as of `--as-of` against the lineups in `--history`: `plan` plans with the measured rates, and `advise` prints the trend in its Rest part. Try it with `Tests/LineupEngineTests/Fixtures/plans/sample-fitness-readings.json` and `Tests/LineupEngineTests/Fixtures/plans/sample-history-with-readings.json` (a longer history than `sample-history.json`, whose two lineups cannot measure a trend), `--as-of 2026-11-13`; the readings are invented for the captured names and agree with the paste of that day. Without the option nothing is measured and `advise`'s Rest part ends with only the game's messages; the sample plan picks the same lineups either way (one value in its table, Dejan Tetek's, differs by 0.1), since no measured rate takes a player to 400 inside five fixtures. `advise` also prints a Scouting part after Depth.

How the engine works, where it is not obvious:

- **Import.** FMRTE copies rows with no header. Column meaning comes from FMRTE's own `config.json` (`ColumnsSettings`), and the importer picks the grid whose column types fit the paste. Squads are imported one at a time (first team, U21, U18). A player with no contract (in the search grid, one with no club) has his contract type, months left and wage left blank by FMRTE, all together; they are read as out of contract, with no months left and no wage, and one of the three blank beside one filled is an error that names the column (found on the owner's first real search result, 19 November 2026, kept as the capture `scouting-search`: the importer had asked for a value in each and refused the paste). A paste in which no row has a wage takes its currency from the asking price, and with neither it is refused. The day a contract ends is read from FMRTE's `Contract.ContractExpiryDate` column when the pasted grid has it (`Player.contractEnds`; the owner's team grid from 23 November 2026, kept as the capture `first-team-with-expiry`): a month, a day and a four-digit year with "/" between, as FMRTE writes it ("6/30/2030"), and a blank cell, a day that does not exist (so a date written day first with a day over 12) or anything else is an error naming the player and the column. A grid without the column, a player with no contract, one whose months left are below zero (a contract that has run out, or an amateur's, which has no end; his cell is not read, since what FMRTE writes there is not known) and a squad saved before it give no day and no error; a date written day first with a day of 12 or under cannot be told from a month-first one and would be read month first. Wages are read in the period FMRTE's settings file names (its top-level `Wages`: Weekly, Monthly or Yearly; none is weekly) and the currency symbol on the pasted amounts, which must be the same on every row. They are kept per week inside the engine (`Player.wagePerWeek`, not always whole), and shown through the squad book's `moneyStyle` (`MoneyStyle`, `Display.wage`), which is the currency of the latest import with wages by the year, as the game shows them, whatever period FMRTE pasted them in (27 November 2026; `MoneyStyle.byYear`, and `SquadBook.money` keeps how the import wrote them); squads held in different currencies raise a squad warning, since there is no exchange rate. The league table has a reader of its own (`Import/LeagueTableImporter.swift`, `LeagueTableImporter.read`). FMRTE copies its standings grid with no header too; a standings layout is any grid in `ColumnsSettings` whose columns include both `TeamName` and `Points` (`FMRTEConfig.standingsGrids`, grids with the same columns kept once; FMRTE's key is `CompetitionStandings`, and `CompetitionGroupStandings` has the same nine columns), and the one whose number of columns is the paste's number of fields is used: none fitting, or two that fit, is refused in a sentence. The rows are split by the squads' splitter (`ClipboardText.rows`) with its floor of 20 fields lowered to 2. It needs `TeamName`, `GamesPlayed`, `Wins`, `Draws`, `Loses`, `GoalsScored`, `GoalsAllowed` and `Points`, every number a whole number with no decimal point and, but for the points (below), no sign, and uses `Position` when the grid has it. A blank team name, a blank or non-numeric cell (naming the team and the column), fewer than two teams, a team twice (names by `PlayerID.normalise`), places that are not 1 to the number of teams each once, wins, draws and losses that do not add up to matches played, and a team that has played more than a season holds (2 × (teams − 1): every league plays everyone twice) each refuse the paste in a sentence. With `Position` the places are the game's own, which takes its word on ties; without it the order is points, goal difference, goals scored, then name, and `orderWorkedOut` is set so the League screen says so. A team whose points are not 3 for a win and 1 for a draw is kept with the pasted points and a warning (`LeagueTableWarning.pointsDoNotFit`: "Marine have 32 points where their results give 35; the table's points are used."), since the game deducts points. For the same reason the points, and only they, may be below zero, written with one leading minus (a hyphen or a true minus); every other number is digits only, and "--3", "-" or "3-" is refused naming the team and the column. Last, the owner's club must be one of the teams, by the app's club name: "Oxford City is not among the 24 teams pasted. Paste your own league's table, or correct the club's name in Settings.", and with no club known "The club is not known yet. Import a squad first."
- **Identity.** A player's key is FMRTE's `Id` column when the pasted grid has it (`fmrte:<id>`); without it, players are identified by name, with a warning. `SquadBook` keeps keys stable across imports and detects moves between squads.
- **Rating profiles.** Ratings come from a `RatingProfile`, which `RatingEngine` and `LineupSelector` take explicitly. `RatingProfile.standard()` is "FM27 engine tests", the owner's chosen default: outfield weights and attribute curves from FM27 match-engine tests (`Resources/rating_profile_fm27.json`), with goalkeeper weights and the way weights differ between positions taken from the FM26 tables (`Resources/rating_tables.json`). "Carried over from FM26" is the old Python's weights, kept for comparison. Design section 8.4 has the formulas.
- **The port check.** The `.fm26Reference` configuration reproduces the old Python (role thresholds, current-ability factor, rounding) and is tested against 594 cases exported from it. Nothing else uses it.
- **Selection.** Rating times condition, sharpness and jadedness factors, solved exactly as an assignment problem, with manual overrides and risk rules that depend on match importance. The owner's choice of a player for a slot beats every rule that would leave him out except being out on loan, and the pick says which rule it overrules. That includes an injury: FMRTE says that a player is injured, not whether he can play through it, and the game passes some injured players fit to play (the owner's report, 18 November 2026). Nothing but the owner's choice picks an injured player, and the choice holds for that fixture only. FMRTE shows that a player is banned, not which matches the ban is for, so a fixture says whether bans count in it (`Fixture.bansApply`); a banned player misses the earliest planned fixture where they do, and no other. Jadedness rates a player at ×1.00 up to 400 (`jadedThreshold`, the game's own "jaded" line), ×0.70 up to 700 (`jadednessSteps`) and ×0.40 above (`jadednessAbove`), and a player above 400 is left out of everything but high-importance matches. `LineupSelector.worth(of:in:_:)` says what any one player would be worth in a slot under a `SelectionRequest` (`SlotWorth`: his rating, fitness factors, adjustments there, the value as `Pick.value` and the lines after the rating line that his pick's reasons would carry, with the rule that leaves him out if one does); it is what his pick shows once the owner chooses him, since a choice changes nobody's value in that fixture, and the planner keeps each fixture's request (`PlannedFixture.selection`: the players on the day's fitness and every adjustment) so the app can ask it (26 November 2026, for the picker). The old ×0.90 between 200 and 400 was removed on 21 November 2026 (the design's call, the owner's to change): it came from the old Python with no source, and no test in any version shows a cost under 400. What jadedness under 400 does cost is counted where it falls, in the slower recovery of condition and in the rule that rests a player before the line (see **Planning** and **Jadedness trend**). Only the `jadednessSteps` entry is labelled derived; `jadedThreshold` is FM27 observation and `jadednessAbove` carried over from FM26.
- **Planning.** `Planner` picks the lineups for the next fixtures in date order. Each player's value is adjusted, with a reason, by the importance rules (consecutive starts, sharpness, development, marked to sell or loan out, loans, retraining, stability) and by a cost for starting him when a bigger fixture follows soon. An unsharp player is favoured ("Needs minutes: sharpness 46% (×1.50)", up to `sharpnessNeedStrengthLow` at 50% sharpness or under in a low fixture and `sharpnessNeedStrengthBuild` in a sharpness one) only when he is in the first or second eleven for the fixture's tactic, or is a successor the fixture favours and not fully sharp: the favour is for a regular who has lost his sharpness, and until 22 November 2026 a low fixture gave it to every player, so one who was unsharp because he never played was worth more unsharp than sharp and the owner's plan started him. Only a sharpness fixture marks down a player in the elevens who is already sharp. A player the owner has marked to sell or to loan out is favoured slightly (`shopWindowFactor`, ×1.03) in low and sharpness fixtures only (a player on a youth contract marked to sell as anyone is; a mark to loan out on him, which can no longer be set but a file may hold, means nothing); the size is the tool's own estimate, and whether playing a player brings offers is untested. A player of 23 or under with potential at least 1.15 times his ability, whom Player Removal calls worth developing (`Removal.isWorthDeveloping`, see Advisors: first choice at a slot he can play, or a reach that could pass the first choice or make the second eleven, or no level), is favoured in low and sharpness fixtures at every slot he can play, by age (until 22 November 2026 only a markedly lower reach was left out, so a player whose reach was cover at best was favoured where the advice would not develop him): ×1.10 at 21 to 23, ×1.07 at 18 to 20, ×1.02 at 17 or under (×1.04 at 17 or under with Professionalism 14 or under). A successor is favoured more, in place of that favour, at the slot where he is close to passing the first choice (a player of 18 to 23 who is close or on course; 17 or under only when close): ×1.15 in low and sharpness fixtures and ×1.05 in medium ones, never in high ones; in a medium fixture only the two closest successors who can be picked are favoured. A first choice at any slot is nobody's successor, a player on loan here gets no favour (the owner's choice: his own players are developed), and neither does a player Player Removal advises to release, sell or terminate, who also takes no place among the two successors at medium; the planner is handed that set (`PlanRequest.advisedToLeave`), which the app and the command line's `plan` work out with Player Removal on the advice's inputs, not at all with Development at 0, and as nobody when the advice fails. A successor who is also retraining at the slot gets whichever is larger: the successor's favour alone, or the floor and the retraining favour together as a non-successor would have them (the floor and retraining on a tie); never all three, and one who would carry the successor's favour at no slot of a medium fixture takes no place among the two. Both favours fall to nothing once he has started four matches in the last thirty days, planned starts included, since the game reads only so much match time in a month (carried over from FM26). The Development setting, 0 to 1 and 1 by default, beside Stability and Saving players, scales each favour as 1 + (factor − 1) × the setting; at 0 no lineup changes, and no outlook is worked out, so a young player missing Professionalism, Ambition or Determination does not stop the plan. The sizes are derived from the research's growth per match by age; the outlooks are worked out once for each tactic with the same code Player Removal uses. Condition, sharpness and jadedness are projected from one fixture to the next; starters are assumed to play 90 minutes and nobody else plays. A player with a measured pair of jadedness rates (see **Jadedness trend**) has his jadedness moved by them in every projection the planner makes (`PlanRequest.rates`): fixture to fixture, the confirmed matches played since the last import and the saving rule; any other player has the fixed figures. Every player's condition comes back more slowly above jadedness 0, measured pair or not. **Resting before the line** (`RestBeforeLine`, adjustment kind `.restedBeforeLine`, beside the saving rule and scaled by the same Saving players setting, so at 0 it does nothing): only for a player with a measured pair, so with the fixed figures nobody is rested by it. His jadedness is projected through the later fixtures twice, starting today and resting today, starting every later fixture he is not rejected for in both. M is the first later fixture he is not rejected for, not of high importance, that weighs more than today's (as the saving rule asks), before which the starting projection, rounded, is above `jadedThreshold` (revised after the whole-branch review: a match off for one of the same worth buys nothing, and a heavier fixture today must not be given up for a lesser one; a later fixture that does not outweigh today's is one he starts in both projections, and the walk goes on); when resting keeps him at or under the line there and he is in M's first eleven with an advantage over the second-eleven player, starting him today costs that advantage times M's importance weight over today's, times the setting, at most `savingCostCeiling`; with no M, or with resting still above the line, or with no advantage, there is no cost. The fixtures are taken in date order, so he is rested in the first fixture where his advantage is worth less than the weighted loss at M, not always the cheapest of all. A fixture the owner has rejected the player for is one he does not start, and cannot be M (revised during the build: the plan's first text counted it). The reason has no full stop, as the saving reason beside it has none: "Rested before he passes 400: at about +31 a start, starting today would leave him jaded for Buxton on Sat 14 Nov" (the 400 is `jadedThreshold`, the date is `AdvisorText.shortDay`, as the saving reason's "Kept fresher for Wealdstone on Sat 21 Nov" now writes it too). A gain that rounds to 0 charges nothing, since the reason would say "+0". Where the saving rule broke a risk rule at this rule's fixture (`SavingAssessment.brokeAt`, every later fixture where it broke one, whichever fixture it named), only the larger cost is added (the saving rule's on a tie), so that fixture's loss is never charged twice; the saving rule's cost is then always at least this rule's. The owner's choice of a player still beats it, and Match Selection shows the reason where it shows the saving reason, as written.
- **Advisors.** They advise; the planner decides who starts. Each is a function of the data it is handed (`Advisors/`). `Elevens` gives the best and second-best elevens at full fitness, injured players kept in and marked; Depth, Training and Player Removal build on those tiers. Depth calls a slot thin when fewer than two players count as cover there: solid (familiarity 15 or over in both phases), rated at least 80% of the slot's first choice there (`depthCoverShare`, carried over from FM26, added on 18 November 2026 after a player at 74% kept a slot of the owner's from being thin), not injured and not first choice elsewhere; a one-day dip in condition does not stop a player counting. A solid player under the 80% is still a stand-in (`DepthOption.isStandIn`, `SlotDepth.standIns`): Player Removal protects real cover at a slot whose cover is at most the line, and also a stand-in too weak to count where the stand-ins are at most the line ("Too few players can step in at left back without him"), so the only other body at a slot is kept until the squad has someone better. Training recommends position retraining for thin slots, and for Training cover that Player Removal advises moving on does not count: a slot is thin when fewer than two of its cover are staying, and the need names who is going (`RetrainingNeed.going`), since Depth still counts him. It also lists the accepted retrainings no thin slot needs (`TrainingReport.retrainingsNotNeeded`). `RetrainingTracker` calls a retraining behind when, over at least six weeks, it has gained something but at under half (`retrainingBehindShare`) the pace that reaches solid in the weeks `Training.estimatedWeeks` gives for the player from where he started; with no gain it is stalled, as before. The planner favours a retrainee at his new position only from familiarity 10, so the plan never plays him there before that (a limit left: the owner's two retrainings had no start in their new positions in thirty confirmed matches); Rest flags players over their own jadedness limit, under the condition floor or on a run of starts, and, at the level watch, a player nothing else lists whose trend as seen, from his own readings alone, would take him past `jadedThreshold` within `onCourseDays` (42 days: the listing reads the lineup's 400, not the player's own limit). Each listed player carries what the readings show of him (`RestAdvice.trend`, `RestTrend`), and `AdvisorText.trendLines` words it in this order: his trend as seen ("Rising about 45 a week over the last 5 weeks, in which he started 6 matches (from 6 readings).", or falling, or "Holding steady" within `steadyPerWeek`) or, with none, "His trend is not measured yet: it needs 4 imports of his squad, and has 2." (his used intervals plus one when he has any, so an import while he was injured or at −500 does not count; else 1 when he has a reading that can still count, on or after the day to measure from, on or before the advice day and within the window, `PlayerTrend.hasCountedReading`; else 0); "At that rate he passes 400 around Sun 7 Nov." when he is rising and at or under the line, and only within `passDateWithinDays` (120 days); what a match off would do, only when he started a match in those weeks, has a measured pair and takes a gain above 0 ("Without a start he falls about 30 a week, and a start adds about 61, so a match off saves about 61." with a drift below 0, or "He holds steady without a start, and a start adds about 61, so a match off saves about 61." when its weekly size is within `steadyPerWeek`, inclusive; with a drift of 0 or above, "He rises about 16 a week without a start, so leaving him out of matches will not bring it down. Lighter training, or rest from training, will.", or "He holds steady without a start, …" within `steadyPerWeek`), followed in brackets by whose rate is not his own ("the first team's rate without a start; his own rate for a start"); and, for a player rising who did not start, "He has not started a match for you in that time: the rise is from training and any matches for another side." A player over a line whose drift is 0 or above has no estimate of days to clear and is told rest from matches will not bring it down, whether or not he started; with a drift below 0 the days to clear count that drift in place of the fixed rate, and beyond `passDateWithinDays` days (revised during the build: a drift just under 0 gave a count of years) no estimate is given and the existing "Clear in more days than the estimate covers" is shown. A holiday keeps its carried-over rate, and the days until condition reaches the floor are projected with his measured pair. Above the players the advice gives a line for each squad whose drift is measured ("First team: a player who does not start rises about 16 a week (from 38 readings since Tue 24 Aug; this tool's estimate).", with "At this training load, leaving players out of matches cannot bring jadedness down." under a squad whose drift is 0 or above), the club's line ("A start adds about 31 (from 14 readings; this tool's estimate).", which the design gave bare and the plan gave its source, as every other trend line has one), "Trend measured from Tue 24 Aug.", and at the foot, under "What the game's messages mean", three lines on what the game's tiredness messages mean with their evidence ("Tired after last match" and "Very tired after last match" describe condition after a match and clear in days; the game calls a player jaded above 400 and no test in any version shows a cost below that; a holiday costs about 0.5% of sharpness a day, `sharpnessDecayPerDay`). Every trend line carries "this tool's estimate", from `jadednessTrendRules`' evidence; Player Removal scores every player of the club's own with a points reason for each rule, and reviews loans to the club; it reads a youth contract (FMRTE pastes `Youth`) and costs it like a full-time one, and a player on one can be sold, marked to sell and released, and cannot be loaned out or marked to loan out (the owner's correction of 22 November 2026 to his earlier statement that he could only be kept or released): at the high and critical levels he follows the full-time rules, except that where a full-time contract would be terminated he is released ("He is on a youth contract that is nearly up, so releasing him is the way to move him on"), since nothing is known about ending a youth contract by agreement; below them he is kept to develop where a full-time contract would be loaned for matches (one engine function, `Removal.isOnYouthContract`, reads it; with 0 months left it is read as no contract). Player Removal costs a release as the wages for the months left plus half a month, because FMRTE's months left is rounded down. A player of 23 or under is judged on his reach, which is this tool's estimate and never a fact: his ability after each coming season is the growth for his age (18 points a season to 18, 14 to 20 and 12 to 26, from FM24 and FM26 tests) scaled for Professionalism, Ambition and Determination, never above his potential, and added up to age 26. The reach is compared, at each slot he can play, with the first and second choice there (a rating is taken to grow with ability from an offset, `ratingAbilityOffset`, fitted on the captured squads and loosely pinned, not in proportion), and a reach below a rival's ability, or below the reach of a rival who is developing too, never passes him; when the second choice is expected to pass the first, the young player must pass him too to be counted as passing the first choice (25 November 2026, above). One line replaces the old elevens, weakest-30%, ability and prospect lines: could pass the first choice (−40), could make the second eleven (−20), could become cover (+15) or markedly lower (+70); a place in either eleven competes with that line, and a backup takes it. The bar between cover and markedly lower is 80% of the first choice's rating, 70% at 16 or under; below it he is markedly lower whoever the second choice is. His Professionalism and Ambition add no line, since his reach already counts them, and a short contract on a player worth developing (one who is first choice at a slot he can play, whatever his level at his other slots, could pass the first choice or make the second eleven, or has no level) says "renew it" at no points; for one not worth developing it keeps its words and points. The advice for him is one of four, with the engine's own sentences and each row showing its working (which says "now, fewer later" only when a later season's growth for his age is lower, at 20 or under, and not from 21, where it is the same every season): keep and develop (17 or under; or, when he is not getting his matches and is not needed as cover, on a youth contract or with twelve months or fewer left, or months unknown), keep and play (he is first choice, or has started a third of the confirmed matches of the last 60 days, or, with fewer than six confirmed, is a solid second choice), loan for matches (18 to 23, not on a youth contract, with more than twelve months left, worth developing, not getting his matches and not needed as cover) or watch (a player worth developing who is not getting his matches and is needed as cover, or one not worth developing who is not kept to play); one not worth developing (cover at best or markedly lower, and first choice at no slot he can play) is never developed or loaned, and is kept to play only when he is in an eleven and playing. A loan for matches is not a removal and is not counted among those advised to leave. These replaced the old prospect and false-prospect rules, except that a false prospect on a full-time contract is sold, not terminated. A player of 24 and over is scored as before; `ImportanceAdvisor` suggests an importance from the competition, the opponent and the schedule, and the owner's choice always wins (a league match starts from a base set by its `LeagueSituation`: title race or relegation fight 100, in contention 80 (the value every league match had before), mid-table 60, nothing to play for 20; the bases are carried over from FM26's table, which that app never called. The situation is the owner's choice by hand when he has made one (`situation`, nil when he has not); else, for a league fixture a pasted league table speaks for (`league`, a `LeagueContext`), the table's; else in contention. A table also raises a match against a side he is battling; see **League table** below. Cups and friendlies are unchanged; `--league-situation` sets the choice by hand on the command line). `OpponentAdvisor.read` reads an opponent's strength from his pasted squad: their club is the most common club on the rows when they carry one (FMRTE's team grid has none, so otherwise the opponent as typed on the fixture); a player loaned to another club is left out; each side's best eleven are its eleven fit players with the highest current ability, whatever their positions, and their average over the owner's (every squad he holds) is compared by the lines `opponentStrengthLines`: 5% above or below is stronger or weaker and 15% much stronger or much weaker (the tool's own estimate, with no test behind it). It refuses a paste whose players are mostly the owner's own (or whose rows carry his club), a side with fewer than eleven fit players, and rows with no club when the opponent is blank, each in a sentence. The reading (club, day, the two averages, the strength, the clubs of those left out) is kept on the fixture; the opponent's players are kept nowhere and enter no advisor. `GamePlanAdvisor.advise` says which game plans to use and to avoid when a match is simulated, by the opponent's strength on the fixture and nothing else, from one entry in `EngineParameters` (`gamePlanRules`, carried over from FM26: the table of `docs/Research/fm26-match-simulation-game-plans.md`). Against a much stronger side: Play for the draw or Play for the win, never Settle for a draw, Strangle the game or Smash and grab; that is the one row that rests on a test of the plans (FM26, ten results a plan), whose points are kept with the rule and quoted. Against a stronger side: Play for the win or Play for the draw. Against a similar or weaker side: Play for the win or No game plan. With no strength set: Play for the win. Those rows are the research's reasoning and carry "this tool's estimate"; the sentences say which is which, and that No game plan was not in the test. Where two plans are named nothing separates them. A rule with no plan to use, or a plan both to use and to avoid, is a parameter problem; Mentoring (`Mentoring.report`) has its own entry point and is worked out per squad. It is handed the squad, the owner's entries (each player's hierarchy level and social group, and when they were entered), the groups the owner has recorded and the personality readings kept at each import, and it suggests groups of three from arrows. An arrow says how strongly one player of a group influences another (None, Light, Average or Significant, the game's words). The owner reads arrows off the game's screen and the engine keeps them for each pair of players; where none has been read it guesses, from the source's hierarchy level and the target's age (23 or under), and says on every line that it is a guess ("expected, not read") and, for one that was read, the day it was read. A group is any three players with no harmful arrow in it, where an arrow is harmful when it is above None and its source is worth less than its target on a counted attribute. A candidate's gain in a group is that of the one arrow into him with the greatest gain (a Light arrow from a much better player can beat a Significant one), never the sum. A player the owner's readings show takes nothing (None from at least three different sources at Influential or above, and nothing above None) is listed as not placed, and can still make up a group as its third member. Of two groups worth the same, the one with fewer members who will go (on loan here or advised to leave) is suggested first, before the older ties (fewer members above Others, more arrows read, the keys), and any member who will go carries the caution that the group ends when he goes (section 13b of the design, added on 15 November 2026 after a group the owner had ended was suggested again unchanged). What was seen of a group the owner ended counts for more than what its arrows promise (section 13c, added on 16 November 2026 after a group ended for doing harm was suggested again): the same three are not suggested again, in a suggestion or a regrouping, when the group was doing harm or had stopped working on the day it ended, judged on the readings up to that day; a candidate whose every helpful group is such a group is not placed, and says so; and a suggested group that puts a member who fell with another member of the group he fell in carries a caution saying what fell and that the cause is not known. Standing above a player by age, a lead for the group and the halving for a shared social group no longer exist. Values are shown as "Professionalism 8, towards 17". It predicts nothing: no gain or score is shown, only the strength and the two values. It also reviews recorded groups (what each member's values did, a warning when a group pulls someone down, a warning when all six of its arrows were read as None, and a warning when it has stopped working after thirteen weeks). It says to break a recorded group up when no member of the club's own who is staying has anything to gain from it by its arrows: as what the tool expects while any of the six is a guess, and not at all while the squad has no level entered to guess from. And it gives at most one regrouping: one recorded group, or two together, whose present members, grouped with the free players in no suggested group by the rule that forms the suggestions, would count for more and for at least 1.5 times as much (`mentoringRegroupFactor`, the tool's own choice; a recorded group with a harmful arrow or with no gain counts for nothing, and one whose gain is not known is never broken up). The suggested groups are left as they are, and the count predicts nothing. It lists players it could not place, with a reason (takes nothing, nobody to influence him, nothing to gain because nobody who influences him is better anywhere it counts, too few players free, no third player free who could join him and a player who could help him without pulling anyone down, his possible influencers already taken, or every helpful group would pull someone down, which is also said when an influencer better in one value is worse by more in another). Every piece of advice carries the weakest evidence behind it, and most of the numbers are carried over from FM26 or the tool's own estimates.
- **League table** (`Advisors/League.swift` for the format, the lines and the reading; `Advisors/ImportanceSuggestion.swift` for its use in the suggested importance; `Reporting/AdvisorText+League.swift` for every word). It sets nothing but the suggested importance: not the planner, the game plan advice, "Their strength" or any other advisor. **The format** (`LeagueFormat`) is three whole numbers the owner enters once: promoted automatically, in the play-offs, relegated. Each is 0 or more, and together they are at most the teams in the table held (`check(teams:)`); a number that breaks this is refused in a sentence ("The play-offs cannot have −1 teams.", "1 promoted, 6 in the play-offs and 4 relegated make 11, more than the 10 teams in the table."), and until all three are entered there is no format and nothing is read. **Byes** (the owner's rule, 19 November 2026): the next power of two at or above the play-off count, less the count (6 gives 2, 5 gives 3, 7 gives 1, 3 gives 1; 0, 1, 2, 4 and 8 give none), going to the highest play-off places ("2nd and 3rd get a bye."). **The lines** (`LeagueLine`) lie after a place: promotion after P, bye after P + byes, play-off after P + play-offs, relegation after teams − R, each only when its number is over 0; a line with no side across it, after the last place or before the first (every team relegated), is left out. In the owner's league (24 teams, 1, 6 and 4) they lie after 1st, 3rd, 7th and 20th. **The reading** (`League.read`, handed the table, the format, the club and the parameters; `LeagueReading`): a season is 2 × (teams − 1) matches, his matches left are that less his played, and a team's most is its points plus 3 for each match it has left. The margin is 6 points, and 3 with one match left (the owner's rule, 19 November 2026). Above a line after place k, he is safe when fewer than k other teams can still reach his points (as if he lost every match left, and counting a side that can only draw level); else the gap is his points less those of the side in place k + 1. Below it, the line is out of reach when at least k other teams already have more points than his most; else the gap is the points of the side in place k less his. Both tests ignore that the other sides play each other, so a line can be called open that is in fact settled, never the other way round. An open line (`LineState`) is close (the gap within the margin), within reach (at most 1 point for each match he has left: this tool's estimate, with no test) or far. **The situation** is the first that holds: every line settled (safe or out of reach), or no lines, is nothing to play for; the promotion, play-off or relegation line close with 10 matches or fewer left is title race or relegation fight; any line close or within reach is in contention; anything else is mid-table. The bye line lifts it to in contention at most. The ten matches are carried over from the old app's table, which gave its top value only in the last ten league matches. The line behind a title-race or in-contention situation (`decidedBy`) is the close line with the smallest gap (for title race, the bye line left out), or with none close the line within reach with the smallest gap, the earlier on a tie. **The sides he is battling** (`rivals`, in table order) are every other team within the margin of his points, ahead or behind, once he has 10 matches or fewer left (`battlingInLastMatches`), and nobody before; nothing else is asked of them, not which line lies between nor matches in hand. The ten is the owner's revision R1 of 19 November 2026: at the start of a season every team is within 6 points of every other. With no match left the season in the table is over: the reading has his place and points, no lines, no situation and nobody battled, and changes no suggestion. All the numbers are one entry, `leagueStandingRules` (`LeagueStandingRules`: margin 6, 3 with one match left, 1 point a match, the last 10 matches for both rules, factor 1.2, 3 points a win, 1 a draw), labelled derived, the weakest of them, with a source saying which rests on what; all league arithmetic is in whole numbers. **Which fixtures a table speaks for** (`League.spokenFor`): as many of the owner's league fixtures as it has matches left, in date order, from those dated after the day it was pasted and those on that day with no lineup confirmed; a confirmed one among them counts as one of the matches. A league fixture beyond them is suggested as with no table, so an old table, or the next season's fixtures, are not read by it. **In the suggestion** (`LeagueContext`, the reading and the fixtures it speaks for): with no choice by hand, a league fixture the table speaks for takes the table's situation, and its first reason names what the table found ("League match, your play-off place is within 6 points: 100"); against a side he is battling (names by `PlayerID.normalise`), whichever way the situation was set, the score is multiplied by 1.2 (this tool's estimate, the size of a much stronger opponent) after the opponent's strength, with a reason ("Buxton are level on points with you (×1.2)", "Spalding are 3 points ahead of you (×1.2)"). The "bigger match follows" rule measures the next fixture the same way, factor in. A suggestion that used the table carries the weaker of the two entries' evidence. **The words** are the engine's: `AdvisorText.standingLines` gives, on the owner's table, "You are 5th on 74 points with 3 matches left.", "Automatic promotion is out of reach: Chester have 87 points and the most you can reach is 83.", "A bye in the play-offs is 3 points away: Spalding, in 3rd, have 77.", "Your play-off place is not safe: Morecambe, in 8th, are 6 points behind you.", "You cannot be relegated.", "League matches read as Title race or relegation fight: your play-off place is within 6 points with 3 matches left (this tool's estimate)." and "Within 6 points of you: Spalding, Hednesford, Buxton, Macclesfield and Morecambe."; the situation line carries "(this tool's estimate)" except for nothing to play for, which is arithmetic. A club in mid-table far clear of a line is told the highest such line he holds, in the situation line ("League matches read as Mid-table: your promotion place is 7 points clear with 5 matches left, and nothing else is within reach (this tool's estimate).") and the base reason ("League match, your promotion place is 7 points clear with 5 matches left"); with none, "nothing is within reach". Above the relegation line and not close: "F, in 6th, are 23 points behind you, across the relegation line." Points below zero are written with a true minus (`AdvisorText.signedNumber`), in these sentences, the warning and the table's rows. The evidence note says the margin is the owner's rule and the rest the tool's estimate: "The places and points are the table's own. The margin of 6 points is your rule (3 with one match left). Which lines are within reach or far, and the ×1.2 for a side within the margin, are this tool's estimate, with no test behind them." (`leagueEvidenceNote`, handed the rules). `AdvisorText+League.swift` also holds the line names drawn on the table ("promoted", "bye", "play-offs", "relegated"), the bye line, the pasted day, the out-of-date and table-stops cautions, the line on a choice by hand that differs, the caution on an opponent not in the table, the menu's "From the table", the empty and no-format lines, the line saying which format is in use (`formatInUseLine`), the key to the mark on a side within the margin (`withinMarginKey`, "Within 6 points of you") and the evidence note; the refusals and the warning are in `ErrorDescriptions`. The owner's table of 19 November 2026 is a test fixture (`Fixtures/captures/league-table.tsv` and its layout), rebuilt from the design's appendix, not captured.
- **Scouting** (`Advisors/Scouting.swift` for who is going, the squad that stays and the needs; `Advisors/ScoutingCandidates.swift` for who is already held, a candidate's judgement and the list; `Reporting/AdvisorText+Scouting.swift` for every word). It is for the squad the owner will have, so it is judged without the players who are going. A player is going when he is on loan at the club, marked to sell, marked to loan out, or advised to leave by Player Removal (`advisedToLeave`; a loan for matches is not among them), and each is counted once, under the first of those reasons in that order. `Scouting.going` works the set out; the command line takes no marks, so it has only the first and last. The elevens and Depth are solved again for the chosen tactic from the players who stay (with nobody going they are the Elevens screen's own), and everything below is judged on them: "first choice" and "second choice" mean those among the players who stay. The need for a slot is of two kinds, with no ranking between them, since nothing measures a weak first choice against a missing stand-in. **A better player**, the first of these that holds: nobody (no first choice, or he is out of position there, with familiarity under 10 in either phase); weak (his rating is 5% or more under the average rating of the outfield first choices, those out of position left out of the average; the weak line, `scoutingWeakShare`, is 0.95 and labelled derived: this tool's estimate with no test behind it); ageing (he is 30 or over, `firstChoiceAgeNamedFrom`, and no player of the club's own of 23 or under, staying or out on loan and not first choice at another slot, is close or on course to pass him at the slot by the bands Player Removal and the planner use; the line says decline is not measured, so it is a prompt to look). The goalkeeper is rated on his own scale, so he is compared by current ability, both his and the outfield first choices' taken through `ratingAbilityOffset` (the way a rating is taken to grow with ability), against the same line, and the line says ability was compared. When today's first choice at the slot is going, the line names him and why, and judges the best who stays ("Sam Reed, the best who stays, rates …"). A weak first choice of 30 or over is named with his age ("Alfie Potter, 37, rates 5.9% under …"), since the weak rule comes before the ageing one and would otherwise hide it. A nobody or weak need is eased when a player of the club's own of 23 or under, staying or out on loan, has a reach rating at the slot that clears the weak line (for the goalkeeper, his reach as ability through the offset), the highest reach naming him; one out on loan is rated at the slot directly, as a pasted player is, against the staying rivals, and the line says where he is ("Max Treml, out on loan at Wallingford, is 18; …"). The ageing rule's successors are the same players: of 23 or under (`developingUpToAge`), staying or out on loan, close or on course to pass him (found on the captured squad: the goalkeeper's line said nobody was on course while a goalkeeper out on loan was). A player who is first choice at another slot eases nothing and is nobody's successor, since he cannot fill both (found on the captured squad: the need at left defensive midfield was shown as eased by the first choice at right defensive midfield). An eased need stays on the list, after the others of its kind, and its line says "his reach would bring him level (this tool's estimate)"; an ageing need is never eased. One helper holds each rule: the weak line (`Scouting.isWeak`, `clearsWeakLine`), the goalkeeper's slot (`isGoalkeeperSlot`, on the in-possession position; the text is handed what was measured and asks nothing about positions) and Depth's cover test (`Depth.isCover`). **More depth**: Depth's own count among those who stay, fewer than two counting as cover (solid, familiarity 15 or over in both phases, rated at least 80% of the first choice, not injured, not first choice elsewhere), with Depth's numbers and sentences, so that the Elevens and Training screens agree. The lines give the count and who counts; the next best against the slot's first choice as a percentage ("The next best, Zac McEachran, rates 6.4% under Fernando Forestieri.", "… rates 2.0% above …" when he rates higher, "The next best is …" with no first choice, "Nobody else can step in." with none); who would count but for an injury, since an injured player is not cover ("Not counting Fernando Forestieri, who is injured."), and, when counting them would lift the slot to the line, "The need lasts only while he is out."; cover who counted today and is going ("Not counting Scott Pollock, who is going"); and players out on loan who are solid there and within that share and would count as cover on their return. Better players are listed nobody first, then weak by the size of the gap, then ageing oldest first, ties by the tactic's slot order; more depth in Depth's order (least cover, then the larger drop to the next best), the needs that last only while players are injured after the others; the slots with neither are listed last as fine. The evidence on a need is the weakest among the entries it read. **A pasted player** (`Scouting.candidates`) is one the owner does not hold. He is held when his key and a held player's are both FMRTE ids and the same, when his club or the club he is on loan at is the owner's, or when a held player has the same name, age and potential ability (the search grid has no id column, so the last rule is how the owner's own players are known); names alone are not matched, so a namesake at another club stays, and the rules are applied again each time the players are judged, so one the owner has since signed and imported drops out. A pasted player the owner has hidden is left out too, after the held test (a player both held and hidden is left out as held): `Scouting.candidates` is handed the hidden players (`hidden:`, nobody by default, the state before players could be hidden), each a `HiddenCandidate`, Codable, of his name as pasted and his potential ability, and `Scouting.isHidden` knows him again by the same normalised name (`PlayerID.normalise`) and the same potential ability; age is not used, since it changes at his birthday, and the search grid has no id. He is not judged (one who could not be rated stops nothing while hidden), is in no group, does not count towards the evidence, and is returned apart as pasted, in paste order (`CandidatesReport.hidden`). Two namesakes with one potential ability are hidden together. The command line takes no hidden players. He is judged at each slot of the tactic where his familiarity is 10 or over in both phases, by the full-fitness rating the Elevens and Depth use; condition, sharpness and jadedness play no part and an injury is only marked. **Today**, against the first and second choice who stay: would start (at least the first choice's rating, or no first choice there), would make the second eleven (at least the second choice's, or there is none in position), would count as cover (at least 80% of the first choice's, `depthCoverShare`) or below cover; the line names who he was compared with and the gap ("rates 6.0% above Ellis Brown, who fills in at left back out of position" when the first choice is out of position there), says when he is not yet solid there (with the two familiarities), and says when he would start at a weak or nobody slot and still be under the weak line himself (at the goalkeeper's slot with the two abilities). **Later**, only for a player of 23 or under (`developingUpToAge`): his reach is `Reach.estimate`, as for Player Removal's young players, and his level (could pass the first choice, could make the second eleven, could become cover, markedly lower), band and working come from the same code, made to take a player who is not in the squad. Every sentence about his reach names its slot ("Not expected to reach the level of cover at left back"); "at any position", Player Removal's words for a squad player, is never said of a candidate, whose other slots may differ. At a slot with no first choice there is no level, and the line gives his reach and whether it clears the weak line ("His reach would rate about 112 at left back, which clears the line for a weak slot", by ability at the goalkeeper's slot). For one who would only be cover the line says the estimate assumes regular matches. A player of 24 or over is "judged as he is today", and from 30 the line says decline is not measured. **Cautions** are Player Removal's own lines (`removalRules`, carried over from FM26), with the value: Consistency, Important Matches, Injury Proneness, Controversy, Temperament and Professionalism on the wrong side of theirs; they carry no points and change no level. He **answers a better-player need** today when he would start at the slot, and later when he is 23 or under and could pass the first choice there; he **answers a depth need** when Depth would count him as cover there (solid, and at least 80% of the first choice's rating, or solid alone with no first choice), whatever his level, so a player far below the first choice who would make the second eleven only because nobody else is there does not. His **headline slot** is the first of: a slot where he answers a better-player need today (in the needs' order); one where he answers a depth need (in theirs); one where he answers a better-player need later; a slot where he would start (the greatest margin over the first choice, then the tactic's order); a slot where, at 23 or under, his reach could pass the first choice (the greatest reach margin, then the tactic's order); otherwise where his level today is best, then his margin is greatest, then the earlier slot, where a place in the second eleven that he would hold while rating under 80% of the first choice ranks below would count as cover (such a place is his only because the second choice there is missing, out of position or weaker still). His **other slots** are shown with the same lines for today as the headline slot and, at 23 or under, one line for later ("Later: could pass Deago Nelson at right back."; `AdvisorText.otherSlotLines`). The **list** has five parts, each player once, under his headline slot: answers a need today (the better-player slots in their order, then the depth slots in theirs), could answer a need later (grouped the same way), would start where there is no need, could pass a first choice where there is no need (each of those two a group for every slot that has a player, in the tactic's slot order, headed by the position alone, `AdvisorText.groupHeading(slot:)`: "Right back"; they were one mixed group each until 22 November 2026, when the owner asked for the best five at a position), and the rest, which is one group (a player who can play no slot is here, last, and says so). The owner picks the order (`CandidateOrder`, Today or Later; it never moves a player between parts): answers today by rating today, or reach rating in Later; could answer later by reach rating in both; would start elsewhere by his margin over the first choice, or his reach margin (reach rating over what the first choice is compared at, minus 1) in Later; could pass elsewhere by reach margin in both; the rest by margin, or reach margin in Later. A player with no reach is placed by today's figure in Later, and the player's key breaks every tie. Each need and each candidate carries the weakest evidence behind it (`basis`), and the candidates' report the weakest among them (`CandidatesReport.basis`); the app shows an evidence note on both tabs. Nothing is predicted and no player or squad is given one score: today and later are two verdicts, and the needs and the reach are this tool's estimates, each with its working.
- **Jadedness trend** (`Planner/FitnessReading.swift` for the readings, `Planner/FitnessTrend.swift` for the rates, `Planner/JadednessRates.swift` for the types and the rules, `Planner/FitnessProjection.swift` for the projection, `Planner/RestBeforeLine.swift` for the planner's rule, `Advisors/Rest.swift` and `Reporting/AdvisorText+Rest.swift` for Rest). The design is the owner's choice of 21 November 2026; the numbers are the design's and the plan's calls, with no test behind them. **A reading** (`FitnessReading`, Codable) is one player on one import day: the day, his jadedness, condition and sharpness, whether he was injured and `includes`, the fixtures of the confirmed lineups waiting for his squad's import when it was taken. Two on one day are one, the later replacing the earlier and keeping both sets of fixtures; every key is required when one is read, so a reading with no `includes` is an error. **The rates** are one function, `FitnessTrend.rates` (readings, confirmed lineups, each player's squad, the day, the day to measure from and the parameters), which returns `FitnessTrends`: each player's trend as seen and measured pair, each squad's drift, the club's gain and the day measured from (the day to measure from when it is set and later than the window's first day; else the earliest reading at an end of a used interval, of any player in a squad, so "Trend measured from" is never later than a squad line's "since"; else the earliest reading in the window; else none). A confirmed lineup belongs to the first of a player's readings that is dated after it or includes its fixture, and starts are counted from the lineups each time the rates are worked out, so a lineup confirmed late or changed after an unlock counts as it now stands. An interval is two readings of one player with none between; it is used when the later is within 42 days of the day asked for (`windowDays`), both are on or after the day to measure from, they are 1 to 14 days apart (`longestGapDays`), he was injured at neither, and neither jadedness is at the floor, −500, where the game holds a rested player. **His trend as seen** (`SeenTrend`) needs no model: the changes of his used intervals over their days, times 7, given with 3 used intervals (`fewestOwnIntervals`, four imports). **Drift**, the change for each day without a start, is the median of his rest intervals (no start in them), his own with 3, else his squad's (the first team, the U21s or the U18s) with 5 intervals (`fewestSharedIntervals`) ending on 3 different days (`fewestSharedDays`), else none. **Gain**, the change for each start, is for each start interval its change less his drift times its days, over its starts; his own median with 3, else the club's (every squad together, with the same 5 and 3), else none; a player with no drift gets no gain of his own, since his own gains are worked out from his drift, and so no measured pair, though he carries the club's gain. **A measured pair** is both rates, used together or not at all (`JadednessRates`; each `MeasuredRate` says whether it is his own, his squad's or the club's); with either missing the projection uses the fixed figures, `jadednessPerMatch` and `jadednessRecoveryPerDay` scaled by training intensity, never one of each. Medians are sorted by value, player key and day and an even count takes the mean of the middle two, so the same readings in any order give the same rates; nothing is clamped, since a median sets aside the odd interval with a holiday, a match the tool was not told of or a lay-off. **The projection** (`FitnessProjection.afterMatch`, `afterDays`, taking `rates:`) adds his gain at a start and his drift on each day without one, either sign, within −500 and `jadednessCeiling` (1,000), and multiplies each day's condition recovery by `conditionRecoveryByJadedness` at the jadedness he started the day with: 1 up to 0, 0.832 at 500, 0.574 at 1,000, in straight lines between (the anchors FM27 measured, from Fishi on fm-arena, 13 November 2026; applying them day by day is the design's own). A default argument of `rates: nil` or `trends: .none` means nothing measured, the state before this plan, not a guessed value. Every number of the trend is in one entry, `jadednessTrendRules`, labelled derived with a source saying which is which: the window 42 days, the longest gap 14, 3 own intervals, 5 shared on 3 days, `onCourseDays` 42, `steadyPerWeek` 5, `keptDays` 120 and `passDateWithinDays` 120; `FitnessModel.problems` checks it. Measured figures are written as whole numbers of their size, with the direction in the words, and days as "Sat 14 Nov" by `AdvisorText.shortDay`. The calls the plan made beyond the design, each the owner's to change: a first reading is taken at the first launch from each squad held (see the app's notes); the club's line says what it rests on; the planner's reason has no full stop; a drift within 5 a week of nothing is written "holds steady", and a measured gain of 0 or below gives no "a match off saves" line and no cost in the plan; a date is given only within 120 days; "it needs 4 imports of his squad, and has 2" counts his used intervals plus one; a player's readings all count under the squad he is in now; a player needing a holiday keeps his holiday estimate even when his drift is 0 or above; and the Saving players explanation gained "and rests them before they are jaded". The design's limits as they stand, and the faults left, are in the plan's closing sections: nothing is measured until four imports, a regular starter's drift is his squad's, a change of training shows slowly unless the owner presses "Measure again from today", and the 400 line was read off five prime-age players. The whole-branch review left these, also listed there: a high-importance fixture more than one match ahead is protected by neither rule, so a jaded player still plays a high match at the jaded factor; the planner's reason does not say whose rate it used; Rest can say leaving him out "will not bring it down" while Match Selection says "Rested before he passes 400", both true, since the match off buys one named fixture; readings are dated by the app's date, so an import made without moving the date mis-sizes an interval or replaces that day's reading, and one with the date set months ahead drops the earlier readings; an import made on match day after the match but before the lineup is confirmed puts the start in the next interval; "Measure again from today" cannot be undone in the app; and a player's pass date is counted from the latest import of any squad, not his own squad's.
- **Offers** (`Advisors/OfferTypes.swift` for the rules, the terms, the record and the suggestion; `Advisors/Offers.swift` for the terms, `Offers.check` and the rounding; `Advisors/OfferMeasures.swift` for what the record shows; `Reporting/AdvisorText+Offers.swift` for every word; `describe(_: OfferError)` in `ErrorDescriptions`). It sets nothing else: not the plan, another advisor or a mark. No test in any version shows what a club accepts, so the terms keep within the one limit known (a club offers only what it can afford, FM26 official) and fill the rest with estimates that say so. **The rules** are one entry, `offerRules` (`OfferRules`, labelled derived, with a source saying which number rests on what): a sale asked at 1.0 of his value, a loan at his value ÷ 192 a week, a counter step of 1.2, 20% of his next fee, money asked later split 44% in instalments over 12 months and the rest after 50 league appearances, a wage step of 10%, 4 weeks to a month in the loan rule, a bid of 5 to 10% of value with no club interested, a step down of 10% at most twice in a row, 5 deals each way and 3 countered sales before anything is measured, and amounts rounded to two significant figures. `Offers.problems` checks them (among other things: no step down below 0 steps, a share of the next fee from 0 to 100, at least one month of instalments and one appearance, finite shares for a bid with no club interested) and is part of `FitnessModel.problems(in:)`; `ask` and `proposal` throw `PlanError.badParameters` while there are problems. Money is whole units, a wage is by the week, a share of a wage or of the next fee is a whole percentage, and a loan fee is by the month. **Three functions**, each handed the player's `OfferSubject` (his value, his wage a week, whether he is a goalkeeper and what a loan is for), the kind, the measures and the parameters: `Offers.ask` (terms to clubs in general, handed his earlier asks of the kind), `Offers.proposal` (to one named club, handed its `ClubFigures` and one deal's rounds: a first proposal, or what to answer to the last round) and `Offers.measures`. The first two return an `OfferSuggestion`: an `OfferAdvice`, its `OfferNote`s in one order (a value of 0, a step down, the kind's own, then the measured figures) and the evidence. `Offers.check` refuses terms of the wrong kind, an amount below 0 or a share over 100%; a figure needed and not entered is `OfferError.missing`, naming the field and the club. **A sale**, T being the sale line × his value, rounded: to clubs in general, ask T with 20% of his next fee, with the lines not to transfer-list him and on the bids reported with no club interested. To a club, money now is T when its transfer budget covers it, else the budget rounded down (revised after the whole-branch review: it had been rounded down even when the club could pay it all), and the rest is asked later, in instalments (44% of it, rounded) and after appearances (the remainder, so the parts always add up), with a caution when something is asked later (naming the budget as entered, "Barnet can spend £35,400 now; the rest is asked later. …") or the club has nothing to spend now, and one when the wage it has left or its highest wage is under his wage, which changes no figure. A club's bid at or above T is accepted; a lower one is countered once, at the smaller of T and the counter step × the bid, keeping the club's money now and adding the difference later, with the larger of its share of the next fee and 20%; a counter that would be at or under the bid (a measured step of 1 or less), and any bid after the club has answered a counter of the owner's, give "Accept it or leave it". A counter needs no budget. After a refusal or no reply the next total is 10% under what the owner last recorded in the deal, at most the present T and never under the club's highest bid, the floor winning when his value was retyped below that bid since (revised after the whole-branch review); the note "Lowered after …" is given only when the new total is below his last, in an ask and in a deal; a third refusal or silence in a row since the club's last round gives "Barnet have turned down or not answered three proposals. Leave it, or ask what they would pay." To clubs in general an ask with "No bid came" lowers the next by 10%, at most T, and a third in a row gives "Three asks have drawn no bid. …", which says to find interest first. An ask still waiting changes nothing: the suggestion is the present terms from his present value, never those of an ask recorded earlier (revised during the build). A step down from nothing stays at nothing. **A loan**: the share of his wage is the smallest of 100%, the loan line × his value ÷ his wage, and for a club its wage left ÷ his wage and, when entered, its highest wage ÷ his wage, rounded down to a step of 10%, with a note saying which limit set it ("40% is within what Barnet have left in their wage budget: £200 a week.", "is within" since the share is rounded down); a fee a month is asked only at 100%, 4 × (what the borrower bears a week − his wage), what a club bears being at most its wage left; a player with no wage has no share, and the fee rule applies. For his development the loan asks a starting place (Regular Starter, or First-Choice Goalkeeper for a goalkeeper, a player whose pasted positions are "GK" and nothing else) with the recall kept; to move his wage it asks no playing time and notes that an optional fee to buy him can be offered at the sale's T. A fee with the recall kept carries the caution that older versions did not allow both. A club's terms: for his development, a starting place is accepted whatever the share, and anything less is sent back with its share and a starting place; to move his wage, its share at or above the suggestion is accepted, and a lower one is sent back at the smaller of the suggestion and its share plus a step; a loan gets one counter too (the plan's call). After a refusal the fee goes first, then a step of the share, never above the present suggestion, down to none of the wage, and then "At none of his wage and turned down, Barnet do not want him on these terms."; to clubs in general the sale's limit of two steps holds. A loan to a club needs its wage budget and wages spent for everything but a development loan's answer to the club's terms. A deal with any accepted round gets `.agreed`, "The deal is agreed." A round's ratio is a sale's total over his value then, or a loan's wage borne a week plus the fee ÷ 4, over his value then; there is none on a value of 0. Each deal gives at most one paid (the highest ratio among the club's rounds and the owner's accepted ones) and one turned down (the lowest among the owner's refused rounds and those the club answered with a lower round); no reply counts for neither; an ask is turned down when a later first bid of a club for the same player and kind, before his next ask, is lower. A line is measured, for sales and apart for loans, from 5 paid and 5 turned down, midway between the two medians, when the median paid is below the median turned down; the counter step is the median, over at least 3 agreed sales in which the owner countered the club's first bid, of the agreed total over that bid (a bid accepted outright is no such deal). Medians sort first, so the same record in any order gives the same figures. Rules for the app:

- The engine decides; the app shows. A view never computes a rating, a reason or a rule. Sentences for errors, warnings and reasons are the engine's (`ErrorDescriptions.describe`, and the reasons on picks and omissions), shown as written. Where the engine has no sentence for something, add one to the engine.
- Every word about advice (level names, actions, verdicts, evidence notes and sentences) comes from the engine (`AdvisorText`, `PositionText`, and the reasons on the reports), shown as written. Core holds only plain labels and headings.
- The Training screen ignores a training action within half a second of the end of the last one (`AppModel.trainingActionInterval`): accepting or turning down a card moves the next card's buttons under the pointer, so a double-click would otherwise act on the next player too.
- Logic for a screen lives in `LineupAppCore` with tests. If a view needs an `if` about data, that is a sign it belongs in Core.
- The look is the Tactics board in `docs/superpowers/specs/2026-11-13-fm27-app-visual-direction.md`. Its two typefaces, Bricolage Grotesque and Figtree, ship with their licences in `LineupAppUI`'s resources and are registered when the app starts. Every colour, typeface and measure comes from `Theme`; no view holds a literal colour, font name or measure.
- Nothing the owner reads is an id or a code: slots are "D L" on a token and "left back" in a sentence; fixtures are named by opponent and date.
- A file that cannot be read gives a notice and a fresh start for that file, and the unreadable file is kept aside. Nothing in a test, a picture run or a sample-data run touches `~/Library/Application Support` or the real clipboard.
- Unsaved changes to a tactic are kept in the model until saved or reverted. Only the earliest planned fixture can be confirmed. A confirmed match keeps its load on its starters in later fixtures until their squad is imported again.

## What the old Python runs, and what it never connected

Runs (per a traced reading of the code):

- Rating core (`rating_calculator.py`): per-player, per-slot rating from position attribute weights, the role's key and secondary attributes, a familiarity factor per phase, and an in-possession/out-of-possession blend.
- Match selection (`ui/api/api_match_selector.py` over `fm_match_ready_selector.py`): that rating times condition, sharpness and jadedness factors, solved as an assignment problem, with manual overrides, per-match rejections, a lineup-stability term, consecutive-start counts from confirmed lineups, and auto-rest rules.
- Advisors: First and Second XI (`api_rotation_selector.py`), Rest (`api_rest_advisor.py`), Training (`api_training_advisor.py` over `fm_training_advisor.py`), Player Removal (`api_player_removal.py`).

Written but never connected (design references, not behaviour to match):

- `state_simulation.py`: forward simulation of fitness.
- `shadow_pricing.py`: shadow pricing beyond a display value.
- `explainability.py`: pick explanations.
- `match_importance.py`: automatic match importance.

The old 155 tests exercise the unconnected modules and parameter helpers. Nothing tests the path that produces lineups.

## Data and privacy

This repository is public. Player data and app state never go in it, except test fixtures under `LineupEngine/Tests/LineupEngineTests/Fixtures/`. The only thing taken from `~/Library/Application Support` is FMRTE's column layouts for the player grids and the standings grid, which the capture tool saves beside each fixture; copy nothing else from there.
