# FM27 Planner Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Lineups for the next several fixtures in date order, where each lineup accounts for projected fitness, the importance of the fixture, what the owner wants from lesser fixtures (sharpness, youth minutes, retraining), and the bigger fixtures still to come.

**Architecture:** A new `Planner/` directory in the `LineupEngine` package. The planner walks the fixtures in date order. For each one it builds per-player adjustments from the importance rules, asks the existing `LineupSelector` for the eleven, then projects every player's condition, sharpness and jadedness to the next fixture's date. `LineupSelector` gains one extension point: adjustments that scale or reduce a player's match-day value and carry their own reason. Nothing reads files; `lineup-cli` gains a `plan` command for trying it on real captures.

**Tech Stack:** Swift 6, SwiftPM, Swift Testing, Foundation only. Same package and conventions as the engine plan.

**Spec:** `docs/superpowers/specs/2026-11-12-fm27-native-app-design.md`, sections 8.5, 8.6, 8.8 and 13. Read 8.6 before any task.

## Global Constraints

- No silent defaults. A bad or missing value is an error that names what is wrong.
- Every tunable number lives in `EngineParameters` (or a `RatingProfile`), with an evidence label and a source. A number in this plan marked [FM27] is `.fm27Measured` or `.fm27Observation` as stated; [FM26] is `.carriedOverFM26`; [derived] is `.derived`. Sources cite the file in `docs/Research/` or the old Python file the number came from.
- Prefer FM27 evidence. Where FM27 research is silent, use the FM26 research and label it as carried over (owner's rule, spec 8.4).
- Every rule gets a test where it changes an outcome and a test where it does not.
- The same inputs always give the same plan: sums and loops run in a fixed order (players by `PlayerID.key`, slots in `SlotID` order, fixtures by date), and the order of the input arrays does not matter.
- Every `switch` over an engine error, warning, cause or adjustment kind is exhaustive, with no `default`. Errors become plain-words sentences in `Reporting/ErrorDescriptions.swift`, each with a test.
- Foundation only. No build warnings. `swift test` passes after every task, including the 594-case FM26 reference check, unchanged.
- Do not modify Python, `ui/`, `.bat` files, existing fixtures, `Resources/rating_tables.json` or `Resources/rating_profile_fm27.json`.
- The repository is public: no player data outside `LineupEngine/Tests/LineupEngineTests/Fixtures/`.
- Paths in tasks are relative to `LineupEngine/` unless they start with `docs/` or are `CLAUDE.md`.
- The planner assumes a starter plays 90 minutes and that nobody else plays. It does not pick a bench or model substitutions.

## Review Focus

Inputs the spec implies but does not spell out, most likely first. Each has a test in the task named.

1. **A fixture dated before the squad snapshot, or two fixtures on one day.** Expected: `PlanError` naming the fixture or fixtures; no plan. (Task 8)
2. **History that no longer matches the squad or tactic**: a confirmed lineup naming a player who has left, or a slot the tactic no longer uses. Expected: ignored for that player or slot, never a crash, never a stability bonus toward a slot that does not exist. (Task 4)
3. **Projected values leaving their range** after many matches or many rest days. Expected: condition stays within 0...1, sharpness within its floor...1, jadedness at or above its floor. (Task 2)
4. **An adjustment large enough to make a value negative** (a big saving cost on the only available player). Expected: the slot is still filled; a slot is never left empty because of an adjustment. (Task 3)
5. **A retraining entry that cannot apply**: a player not in the squad, or a position the tactic does not use. Expected: no adjustment, no error. (Task 6)

New parameters (names are the stored property names):

| Name | Value | Evidence and source |
|---|---|---|
| `matchConditionCost` | 0.25 | [FM26] `physical-condition.md`: 100% to about 75% over 90 minutes |
| `staminaCostPerPoint` | 0.015 | [derived] SI says Stamina is a stronger factor in FM27 (`fm27-condition-fatigue-sharpness.md`); the size is this design's guess, three times the branch's slope |
| `positionConditionLoad` | GK 0.2; D (C) 0.8; D (L), D (R), WB (L), WB (R), DM 1.2; every other position 1.0 | [FM26] branch `fm_match_ready_selector.py` (1.2 and 0.8) and `ui/api/state_simulation.py` (goalkeeper); no FM27 evidence |
| `conditionRecoveryPerDay` | curve over current condition: (0.70, 0.124), (0.80, 0.0813), (0.90, 0.0275), (1.00, 0) | [FM26] fm-arena rest-day test quoted in `fm27-condition-fatigue-sharpness.md` (7,000 to 8,240; 8,000 to 8,813; 9,000 to 9,275) |
| `naturalFitnessRecoveryPerPoint` | 0.0167 | [FM26] branch `state_simulation.py` (`0.5 + NF/100`, relative to Natural Fitness 10) |
| `trainingIntensityRecovery` | low 1.2, medium 1.0, high 0.8 | [FM26] branch `scoring_parameters.py`; FM27 testers report the same direction without numbers |
| `sharpnessGainPerMinute` | 0.001 | [FM27 measured] ZaZ, `fm27-condition-fatigue-sharpness.md` |
| `sharpnessGainTaper` | curve over current sharpness: (0.65, 1.0), (0.80, 0.667), (0.90, 0.222) | [FM26] `physical-condition-claude.md`: 9%, 6% and 2% per 90 minutes; FM27 did not test high sharpness |
| `sharpnessDecayPerDay` | 0.005 | [FM27 measured] same source; none on the day after a match |
| `sharpnessDecayNaturalFitnessPerPoint` | 0.08 | [FM26] `physical-condition-claude.md`: Natural Fitness 20 loses about a fifth of what 10 loses |
| `sharpnessFloor` | 0.35 | [FM27 observation] `fm27-condition-fatigue-sharpness.md` |
| `jadednessPerMatch` | 60 | [FM26] fm-arena, +50 to +70 per match |
| `jadednessRecoveryPerDay` | 20 | [FM26] fm-arena, one rest day removes about 20 |
| `jadednessFloor` | -500 | [FM27 observation] editor range, rested players sit at exactly -500 |
| `assumedMinutes` | 90 | [derived] the planner does not model substitutions |

Rules:

- **Match.** Condition falls by `matchConditionCost × positionConditionLoad[position] × (1 - (Stamina - 10) × staminaCostPerPoint)`, not below 0. Sharpness rises by `sharpnessGainPerMinute × assumedMinutes × taper(current sharpness)`, not above 1. Jadedness rises by `jadednessPerMatch`. `daysSinceMatch` becomes 0.
- **Each day without a match**, applied one day at a time:
  - Condition rises by `curve(condition) × (1 + (Natural Fitness - 10) × naturalFitnessRecoveryPerPoint) × trainingIntensityRecovery[intensity]`, not above 1.
  - Sharpness falls by `sharpnessDecayPerDay × f`, where `f` is 1 for Natural Fitness 10 or less and `1 - (Natural Fitness - 10) × sharpnessDecayNaturalFitnessPerPoint` above it, not below `sharpnessFloor`. A player already below the floor is left where he is. There is no decay on the first day after a match (`daysSinceMatch == 0`).
  - Jadedness falls by `jadednessRecoveryPerDay × trainingIntensityRecovery[intensity]`, not below `jadednessFloor`.
  - `daysSinceMatch`, when not nil, rises by 1.
- A missing Stamina or Natural Fitness attribute is an error (`RatingError.missingAttribute`), which is why both functions throw.
- `FitnessModel.problems(in:)` also reports: an empty recovery or taper curve, a `positionConditionLoad` missing any of the 14 positions, and a training-intensity table missing a level.

### Task 3: Adjustments in the lineup selector

**Files:**
- Modify: `Sources/LineupEngine/Selection/LineupSelector.swift`, `Sources/lineup-cli/Report.swift`
- Test: `Tests/LineupEngineTests/LineupSelectorTests.swift`

**Interfaces:**
- Produces:
  ```swift
  public struct Adjustment: Equatable, Sendable {
      public enum Kind: String, CaseIterable, Sendable {
          case loanedIn, consecutiveStarts, needsSharpness, development, retraining, stability, savedForLater
      }
      public let kind: Kind
      public let factor: Double     // multiplies the match-day value; 1 changes nothing
      public let cost: Double       // subtracted, in rating points; 0 changes nothing
      public let reason: String     // a full sentence fragment the pick shows as it is
      public init(kind: Kind, factor: Double = 1, cost: Double = 0, reason: String)
  }
  // SelectionRequest gains, all defaulted so existing call sites compile unchanged:
  //   public var adjustments: [PlayerID: [Adjustment]] = [:]                 // apply in every slot
  //   public var slotAdjustments: [PlayerID: [SlotID: [Adjustment]]] = [:]   // apply in that slot only
  //   public var fitnessIsProjected: Bool = false
  // Pick gains:  public let adjustments: [Adjustment]      // those applied to this player in this slot, in Kind order
  // OmissionCause gains:  case heldBack([Adjustment.Kind])
  ```

Rules:

- A pick's value is `rating.value × fitness.product × (product of factors) - (sum of costs)`. With no adjustments it is exactly today's value.
- The solver maximises the adjusted value. The ideal eleven used for omissions stays unadjusted.
- A slot is never left unfilled because of an adjustment: when an adjusted value is zero or negative the player is still a candidate (Review Focus 4). If the solver cannot take negative values, shift the values it is given, not the reported ones.
- A pick's `reasons` gain each applied adjustment's `reason`, after the fitness lines and before "Chosen by you".
- When `fitnessIsProjected` is true the fitness lines read "Projected condition 91% (×0.95)", and likewise for sharpness and jadedness.
- An omitted ideal player who is not excluded and not displaced by an override, and who has any adjustment with a factor below 1 or a cost above 0 in his ideal slot, has cause `.heldBack` with those kinds in `Kind` order and reason "Left out: " followed by those adjustments' reasons joined with "; ". Otherwise the existing causes apply.
- Overrides ignore adjustments: an overridden player is placed whatever his value, and his pick still lists them.
- `Report.swift` prints nothing new of its own: the adjustment reasons arrive in `reasons`.

- [ ] **Step 1: Write the failing tests**
  - `aRequestWithoutAdjustmentsGivesTheSameLineupAsBefore`: every pick's value and reasons equal the unadjusted run.
  - `aFactorBelowOneCanCostAPlayerHisPlace` and `aFactorCloseToOneDoesNot`: two candidates for one slot, 5% apart; a 0.90 factor on the better one flips the pick, 0.99 does not.
  - `aCostIsSubtractedInRatingPoints`: the pick's value equals rating × fitness − cost within 1e-9.
  - `aSlotAdjustmentAppliesOnlyInThatSlot`: a 1.5 factor for a player at one slot does not change his value at another.
  - `anAdjustmentNeverLeavesASlotEmpty`: the only available goalkeeper with a cost of 1,000 is still picked, with a negative value.
  - `adjustmentReasonsAppearOnThePickInKindOrder`.
  - `projectedFitnessIsLabelledAsProjected`.
  - `anIdealPlayerLeftOutByAnAdjustmentSaysWhy`: cause `.heldBack([.savedForLater])`, reason "Left out: " plus the adjustment's reason.
  - `anOverrideBeatsAnAdjustment`.

  ```swift
      public init(_ lineups: [ConfirmedLineup])                       // any order; one lineup per fixture id, the later entry wins
      public func adding(_ lineup: ConfirmedLineup) -> StartHistory
      /// Starts in a row up to but not including `day`, counting back from the most recent lineup.
      public func consecutiveStarts(of player: PlayerID, before day: Day, windowDays: Int) -> Int
      /// The slots he started in before `day`, newest first, at most `limit`.
  ```

New parameter: `consecutiveStartWindowDays` = 4 [derived]. Source: `player-rotation-guide.md` (one match a week needs little rotation; rotation matters when matches come two or three a week), so a start only extends a run when it came within four days of the next match.

Rules:

- Only lineups dated before `day` count. Walk back from the most recent. The run is 0 if the most recent lineup is more than `windowDays` before `day`, or he did not start it. Each earlier lineup extends the run by 1 if he started it and it is within `windowDays` of the lineup after it; otherwise the walk stops.
- `recentSlots` skips lineups he did not start. A player or slot that no longer exists is simply data (Review Focus 2): nothing here checks the squad or tactic.
- The old app read history oldest-first as if newest-first and kept the ten oldest entries (spec 11). The tests pin the right order.

### Task 6: The importance rules

**Files:**
- Create: `Sources/LineupEngine/Planner/ImportanceRules.swift`
- Modify: `Sources/LineupEngine/Parameters/EngineParameters.swift`
- Test: `Tests/LineupEngineTests/ImportanceRulesTests.swift`

**Interfaces:**
- Consumes: `Adjustment`, `StartHistory`, `SquadTiers`, `Retraining`, `PlanSettings`, `SlotAssignment`, `LoanStatus`, `Importance`, `Day`.
- Produces:
  ```swift
  public struct RuleContext: Sendable {
      public var importance: Importance
      public var date: Day
      public var assignments: [SlotAssignment]
      public var ownClub: String?
      public var history: StartHistory
      public var tiers: SquadTiers
      public var retraining: [Retraining]
      public var stability: Double
  }
  public enum ImportanceRules {
      /// Every adjustment except saving players for later (Task 7), for one player on his current fitness.
      public static func adjustments(for player: Player, context: RuleContext, parameters: EngineParameters)
          -> (everySlot: [Adjustment], bySlot: [SlotID: [Adjustment]])
  }
  ```

The rules, with their parameters. Factors are shown in reasons to two decimals. "IP position" is the slot's in-possession position.

1. **Loaned in** (every slot). When `LoanStatus.of` is `.loanedIn`: `loanedInFactor` = medium 0.95, low 0.85, sharpness 0.85, high 1.0 [FM26, branch `ui/api/api_match_selector.py`]. Reason: "On loan here: marked down so the club's own players get the minutes (×0.85)". No adjustment at high.
2. **Consecutive starts** (by slot; medium, low and sharpness only). `n = history.consecutiveStarts(of:before:windowDays:)`. `consecutiveStartSteps` [FM26, branch `fm_match_ready_selector.py`], by IP position, the highest step reached:
   - D (L), D (R), WB (L), WB (R), DM: 2 → 0.90, 3 → 0.75, 4 → 0.60
   - M (L), M (C), M (R), AM (L), AM (C), AM (R), ST (C): 3 → 0.90, 4 → 0.80, 5 → 0.70
   - D (C), GK: 5 → 0.90, 6 → 0.80

### Task 7: Saving players for bigger fixtures

**Files:**
- Create: `Sources/LineupEngine/Planner/SavingPlayers.swift`
- Modify: `Sources/LineupEngine/Parameters/EngineParameters.swift`
- Test: `Tests/LineupEngineTests/SavingPlayersTests.swift`

**Interfaces:**
- Consumes: `FitnessProjection`, `FitnessModel.factors`, `RiskRules`, `SquadTiers`, `Fixture`, `ProjectedFitness`, `Adjustment`.
- Produces:
  ```swift
  public struct LaterFixture: Sendable {
      public var fixture: Fixture
      public var tiers: SquadTiers        // for that fixture's tactic
  }
  public enum SavingPlayers {
      /// The cost, in rating points, of starting `player` today at `position`, given the fixtures still to come.
      /// nil when there is none.
      public static func adjustment(for player: Player, fitness: ProjectedFitness, position: Position,
                                    today: Fixture, later: [LaterFixture], settings: PlanSettings,
                                    parameters: EngineParameters) throws -> Adjustment?
  }
  ```

New parameter: `importanceWeights` = high 3.0, medium 1.5, low 0.8, sharpness 0.1 [FM26, branch `scoring_parameters.py`].

The formula (spec 8.6 and 15 leave it to the builder; it uses slot ratings, importance, proximity and projected fitness, and scales to zero):

- Only later fixtures with a greater weight than today's count. So nothing is ever saved at a high fixture.
- For each such fixture `m`, and only if the player is in `m`'s first eleven:
  - `rest` = his fitness at `m`'s date if he does not start today: `afterDays(gap)`.
  - `play` = his fitness at `m`'s date if he does: `afterMatch` at `position`, then `afterDays(gap)`.
  - `drop = max(0, product(rest) - product(play))`, the products of the three fitness factors.
  - `loss = min(advantage in m, rating in his slot in m × drop)`. If `play` would break a risk rule at `m` that `rest` would not (condition below the floor; jaded, unless `m` is high), `loss = advantage in m`.
  - contribution = `loss × weight(m) / weight(today)`.
- Cost = `settings.savingPlayers ×` the sum of contributions. No adjustment when the cost is 0.
- Proximity enters through the projection: the nearer the fixture, the larger the drop. A player short of sharpness can gain more from playing than he loses in condition; then the drop is 0 and there is no cost.
- Reason, naming the fixture that contributes most: "Kept fresher for Wealdstone on 2026-11-21: starting today would cost about 6.2 there". The figure is that fixture's unweighted loss to one decimal.

  ```swift
  public struct PlanRequest: Sendable {

  }
  ```

How it runs:

1. Check settings and dates (Review Focus 1). Sort fixtures by date and keep the first `settings.horizon`. No fixtures gives an empty plan.
2. Start every player from `ProjectedFitness(player)`, moved forward by the days from `asOf` to the first fixture. History starts as `StartHistory(request.confirmed)`.
3. For each fixture in order:
   - Copy each player with his projected condition, sharpness and jadedness (rounded to the nearest whole number).
   - Compute `SquadTiers` for the fixture's tactic, and for each later planned fixture's tactic.
   - Build adjustments: `ImportanceRules` for every player, and `SavingPlayers` for every player at every slot.
   - Select with the fixture's overrides and rejections, `isNextFixture` true for the first fixture only, and `fitnessIsProjected` true when any day has passed since `asOf` or a match has been played in the plan.
   - Record the lineup in the history as if confirmed, so later fixtures see its starts and slots.
   - Starters (overridden ones too) take `afterMatch` at their slot's in-possession position. Then everyone takes `afterDays` to the next fixture.
4. An injured player stays injured for the whole plan: FMRTE gives no return date.
